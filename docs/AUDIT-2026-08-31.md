# Auditoría técnica — 31 de agosto de 2026

## Resumen ejecutivo

La aplicación productiva está operativa. Vercel no mostró errores de runtime durante los últimos 7 días y los deployments recientes de producción se encuentran en estado `READY`.

La principal deuda detectada no es un fallo visible para el usuario sino **de organización, reconstrucción y trazabilidad**: existen componentes activos en Supabase que no están completos en GitHub, numerosos workflows/scripts de parche histórico y un hosting secundario de GitHub Pages que actualmente falla en cada ejecución.

No se recomienda una limpieza destructiva inmediata. El saneamiento debe hacerse por capas, conservando compatibilidad con todas las chapitas ya emitidas.

## GitHub Actions

### Workflow útil y permanente

`hosting-check.yml` funciona como smoke test del hosting Vercel: exige HTTP 200 y comprueba que la página contenga `Patas a Casa`. Este tipo de workflow debe conservarse y ampliarse gradualmente.

### Workflow con error actual

`pages.yml` intenta desplegar todo el repositorio en GitHub Pages. Su última ejecución sobre `main` falló en `Setup Pages`, mientras Vercel permaneció saludable.

Debe existir una sola decisión explícita:

- **si GitHub Pages es backup intencional:** repararlo y documentar su finalidad;
- **si Vercel es la única producción:** quitar el workflow para eliminar una falsa alarma recurrente.

### Workflows históricos de parche

Se detectaron múltiples workflows asociados a cambios concretos (`add-*`, `fix-*`, `apply-*`, etc.). Al menos uno, `add-lost-details.yml`, ejecuta un script Python, modifica archivos productivos, crea un commit y hace `git push`.

Ese patrón no debería ser el mecanismo estándar de mantenimiento. Un workflow permanente debería principalmente **validar** el código, no reescribirlo y publicarlo automáticamente.

## Arquitectura frontend

La aplicación sigue un modelo estático/monolítico válido para el tamaño inicial del proyecto, pero actualmente concentra mucha lógica en:

- `index.html` (~43 KB)
- `mi-cuenta/index.html` (~81 KB)

Esto dificulta ubicar errores por dominio. La estructura objetivo futura puede separar:

```text
assets/
  css/
    base.css
    public-profile.css
    account.css
  js/
    config.js
    api.js
    auth.js
    activation.js
    public-profile.js
    account.js
```

No realizar esta extracción junto con la limpieza de workflows. Debe ser una refactorización aislada con pruebas visuales y funcionales.

## Orden de saneamiento recomendado

### Fase 1 — documentación y fuentes de verdad

Hecho en esta rama:
- README profesional;
- mapa de arquitectura;
- modelo de seguridad;
- procedimiento de operación;
- esta auditoría.

### Fase 2 — infraestructura reproducible

- capturar Edge Functions vivas;
- clasificarlas `active`, `legacy`, `test` o `candidate-for-removal`;
- versionar todas las productivas;
- crear baseline de esquema/migraciones.

### Fase 3 — CI limpio

- decidir GitHub Pages;
- conservar smoke tests;
- archivar/retirar automatizaciones de un solo uso;
- impedir que workflows históricos modifiquen `main` accidentalmente.

### Fase 4 — frontend mantenible

- separar configuración/API/UI en módulos;
- mantener las URLs públicas intactas;
- agregar pruebas mínimas para perfil, activación, login y cuenta.

### Fase 5 — hardening

- leaked password protection;
- revisar RPC privilegiados;
- CSP/HSTS cuando el frontend lo permita.

## Criterio de seguridad para la limpieza

Nada se elimina hasta que se cumplan conjuntamente:

1. no tiene referencias activas;
2. no muestra uso relevante en logs;
3. existe copia versionada o historial recuperable;
4. preview funciona sin él;
5. las chapitas existentes siguen resolviendo sus URLs y perfiles.

## Conclusión

El sistema no necesita una reescritura. Necesita convertir el estado actual —que funciona— en una plataforma **reproducible, observable y predecible**. La prioridad es reducir fuentes de verdad paralelas y automatizaciones históricas antes de hacer refactors visuales o de arquitectura interna.
